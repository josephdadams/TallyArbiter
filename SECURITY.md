## Reporting a Vulnerability

**Please do not open a public issue or pull request for a security vulnerability.**

Report it privately through GitHub Security Advisories:

👉 **[Report a vulnerability](https://github.com/josephdadams/TallyArbiter/security/advisories/new)**

This keeps the details between you and the maintainers until there's a fix available. We take security issues seriously and will try to get a hotfix out as soon as we can. You'll get credit in the advisory unless you'd rather not.

If you can't use Security Advisories for some reason, open an issue asking us to get in touch — but don't include the details.

### What to include

The more of this you can provide, the faster it gets fixed:

- **A reproduction** — the request you sent and the response you got back, against a running instance
- **The impact** — what an attacker actually gains, and what access they need to start with (same LAN? an existing login? nothing?)
- **Version and distribution** — Desktop, CLI, Docker, or from source
- **A suggested fix**, if you have one in mind

## Threat model

Some context, so you can tell a real finding from a false positive.

Tally Arbiter is a broadcast production tool. It's designed to run on a **trusted production LAN** alongside the switchers, cameras, and listener devices it talks to. It is not designed or hardened to be exposed directly to the internet, and we don't recommend deploying it that way. If you need remote access, put it behind a VPN or an authenticating reverse proxy.

Given that, a few things are **intentional** and aren't vulnerabilities on their own:

- `/health` and `/version` are unauthenticated. They exist for container health checks and monitoring — the Docker image's `HEALTHCHECK` depends on `/health` being reachable.
- `/` and the static UI assets are served without authentication. The UI is a client-side app; it authenticates when it connects.
- The real control plane is Socket.IO, and privileged actions there are gated behind role checks. That's the surface worth scrutinizing.

Things we **do** consider security issues: authentication or role-check bypass on the Socket.IO API, ways to read or overwrite `config.json` (it holds credentials and JWT signing material) without authorization, injection into the commands sent to cameras and switchers, and anything that lets an unauthenticated LAN client take actions that should require a login.

Also worth knowing how the seeded accounts work. A new install still seeds `admin` and `producer` with the documented default password, but both accounts are flagged: the server refuses every privileged action for them and the UI forces a new password on first login, so the default is only ever valid for the one login that replaces it. Reporting that a **fresh** install accepts `admin`/`12345` is therefore not a finding.

Installs created before that change are **not** forced to rotate — locking an operator out mid-production would be worse than the exposure. Those accounts keep working on the default password, and Tally Arbiter warns about them on every startup and in Settings > Users. If you find an install in that state, the fix is to change the password; it isn't a new vulnerability. What _would_ be a finding is a way to get past the forced change on a fresh install, or to clear the flag without knowing the current password.

## A note on automated scanners and AI-generated reports

We get automated security reports, and we do read them. But a scanner rule ID and a severity rating are not a vulnerability report — generic web-application rules produce a lot of noise against a LAN tool with an intentionally open HTTP surface.

If your report or PR is generated by a scanner or an AI agent, please make sure a human has verified it against a running instance first, and include the reproduction described above. Reports that only restate scanner output, or PRs whose description doesn't match their diff, will be closed. See the [pull request template](.github/pull_request_template.md) for what a security PR needs.

## Contributing a fix

This project is very community-friendly — if you know how to fix it, we'd love the help. For anything sensitive, please coordinate with us through the advisory first so we can time the disclosure with a release, rather than opening a public PR that explains the exploit.

Go check out our [Code of Conduct](https://github.com/josephdadams/TallyArbiter/blob/master/CODE_OF_CONDUCT.md) and get started.
